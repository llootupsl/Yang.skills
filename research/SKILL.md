## 集成原则

所有调研方案的集成遵循以下三条核心原则：

1. **独立适配器模式**：所有外部工具封装在 `adapters/` 目录下，保持核心skill逻辑与外部依赖解耦
2. **可切换引擎**：每个适配器支持多引擎切换
3. **渐进式增强**：新引擎作为可选增强，降级路径明确，不行就回退旧引擎

| 关系层级 | 描述 | 典型场景 |

## 调研成果转化为 Skill 改进的流程

### 转化流程总览

```
调研成果 → Skill 改进的标准化流程：

  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ 调研完成 │──→│ 可行性   │──→│ 集成设计 │──→│ 适配器   │──→│ 灰度发布 │
  │         │    │ 评审     │    │         │    │ 开发     │    │         │
  └─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
       │              │              │              │              │
       ▼              ▼              ▼              ▼              ▼
  输出：调研报告   输出：评审结论   输出：集成方案   输出：适配器代码  输出：发布决策
  + 推荐方案      (通过/搁置/     + 适配器接口    + 降级路径      (全量/回滚/
                  否决)           + 降级路径      + 单元测试      继续灰度)
```

### 各阶段详细说明

#### 阶段 1：调研完成

- **输入**：调研子模块的完整报告（如 asr-comparison.md）
- **输出**：推荐方案 + 备选方案 + 风险评估
- **质量门禁**：调研报告 MUST 包含至少 2 个方案的对比分析

#### 阶段 2：可行性评审

- **评审维度**：

| 维度 | 评审标准 | 权重 |
|------|---------|------|
| 技术可行性 | 方案是否可在当前技术栈中实现 | 30% |
| 集成成本 | 需要多少开发工作量（人天） | 20% |
| 性能影响 | 对现有 skill 的延迟/吞吐影响 | 20% |
| 降级路径 | 方案失败时能否回退到现有实现 | 15% |
| 维护成本 | 长期维护的复杂度 | 15% |

- **评审结论**：
  - **通过**：进入集成设计阶段
  - **搁置**：记录搁置原因，放入待办队列，等待条件成熟
  - **否决**：记录否决原因，关闭该调研方向（除非出现重大技术变化）

#### 阶段 3：集成设计

- **设计要求**：
  1. 遵循独立适配器模式（`adapters/` 目录）
  2. 支持多引擎切换（新引擎作为可选增强）
  3. 降级路径明确（新引擎不可用时回退旧引擎）
  4. 对现有 skill 的调用接口零变更（内部实现可变，外部接口不变）

- **输出文档**：集成方案设计文档，包含：
  - 适配器接口定义
  - 引擎切换机制
  - 降级回退策略
  - 测试计划

#### 阶段 4：适配器开发

- **开发规范**：
  - 适配器代码放置在 `adapters/{engine_name}/` 目录
  - 每个适配器 MUST 实现标准接口（定义在 `adapters/base.py`）
  - MUST 包含降级路径测试（模拟新引擎不可用时的回退行为）
  - MUST 包含性能基准测试（与旧引擎的延迟/质量对比）

#### 阶段 5：灰度发布

- **发布策略**：
  1. 先在 Solo 模式下验证（不影响产线）
  2. 在 Stage2 盲预测中灰度（预测不阻塞产线）
  3. 在 Stage3 复盘中验证（对比新旧引擎的输出差异）
  4. 全量发布 + 旧引擎保留 2 个版本作为降级备份

## 调研优先级判定规则

### 优先级矩阵

调研优先级由"对 Skill 体系的影响程度"和"实施难度"两个维度共同决定：

```
                    实施难度
                 低        中        高
              ┌────────┬────────┬────────┐
         高   │  P0    │  P1    │  P2    │
影响程度   中   │  P1    │  P2    │  P3    │
         低   │  P2    │  P3    │  P4    │
              └────────┴────────┴────────┘

  P0 = 立即执行（高影响 + 低难度 = 快速胜利）
  P1 = 优先执行（高影响中难度 或 中影响低难度）
  P2 = 计划执行（高影响高难度 或 中影响中难度 或 低影响低难度）
  P3 = 排期执行（中影响高难度 或 低影响中难度）
  P4 = 暂缓执行（低影响 + 高难度 = 投入产出比低）
```

### 影响程度判定标准

| 影响等级 | 判定标准 | 示例 |
|---------|---------|------|
| **高** | 满足以下任一：<br>① 直接影响核心闭环（选题→预测→复盘）的准确性<br>② 影响校准样本的质量或数量<br>③ 解决当前 Skill 的已知关键缺陷 | ASR 精度提升直接影响对标转录质量 → 影响校准样本质量 |
| **中** | 满足以下任一：<br>① 增强辅助 skill 的能力（如热点监控、发布优化）<br>② 提升系统稳定性或可维护性<br>③ 降低运营成本 | 发布时间优化 → 提升发布效果但不影响核心闭环 |
| **低** | 满足以下任一：<br>① 仅改善用户体验（不影响核心功能）<br>② 面向未来需求的预研<br>③ 探索性调研（无明确集成目标） | 多 Agent 框架对比 → 架构参考，无即时集成需求 |

### 实施难度判定标准

| 难度等级 | 判定标准 | 示例 |
|---------|---------|------|
| **低** | 满足以下全部：<br>① 无外部依赖或依赖已安装<br>② 适配器开发 ≤ 3 人天<br>③ 无需修改现有 skill 接口 | 词典规则情感分析 → 纯 Python 实现，无外部依赖 |
| **中** | 满足以下任一：<br>① 需要安装新的外部依赖<br>② 适配器开发 3-10 人天<br>③ 需要修改现有 skill 的内部实现 | 多平台热点监控 → 需要 API key 配置和 Playwright 适配 |
| **高** | 满足以下任一：<br>① 需要 GPU 或特殊硬件<br>② 适配器开发 > 10 人天<br>③ 需要修改现有 skill 的外部接口<br>④ 存在数据隐私/合规风险 | 深度学习情感分析 → 需要 GPU 推理环境 |

### 当前调研方向的优先级评定

| 调研方向 | 影响程度 | 实施难度 | 优先级 | 理由 |
|---------|---------|---------|--------|------|
| 中文ASR引擎 | 高 | 低（方案A）/ 中（方案B/C） | P0（方案A）/ P2（方案B/C） | ASR 直接影响对标转录质量，方案A（低难度）为 P0 |
| 中文情感分析 | 中 | 低（词典规则）/ 高（深度学习） | P1（词典规则）/ P4（深度学习） | 词典规则方案低难度中影响，深度学习投入过大 |
| 热点趋势监控 | 中 | 中 | P2 | 多平台适配增加复杂度，但对 yang-trends 有实质增强 |
| 发布时间优化 | 中 | 中 | P2 | Multi-Armed Bandit 实现适中，效果需验证 |
| 视频质量评估 | 高 | 高 | P2 | 影响大但实施难度高，需分阶段推进 |
| 多Agent框架 | 低 | 高 | P4 | 架构参考性质，无即时集成需求 |
