# yang-persona · 创作人设档案管理

> **前置条件**：项目已 init（.yang-state.json 存在）
>
> **闭环位置**：独立工具，可随时调用
>
> **产生**：`.yang-persona.md` + 更新 `.yang-state.json` 中的 `persona_exists` / `persona_version`

---

## 前置条件检查

读取 `.yang-state.json`：
- 若不存在 → 拒绝执行："请先运行 yang-init 初始化项目"

读取 `.yang-persona.md`（若存在）：
- 若存在 → 展示当前人设概览 + 提供编辑选项
- 若不存在 → 进入新建人设流程

---

## 工作流

### Step 1: 确定操作模式

> 🔍 **CHECKPOINT 0**：操作模式（查看/编辑/新建）已确定

根据触发词和 `.yang-persona.md` 存在性决定：

| `.yang-persona.md` 存在 | 触发词含"编辑"/"修改" | 触发词含"看"/"我的" | 其他触发词 |
|---|---|---|---|
| 是 | → 编辑模式（Step 3） | → 查看模式（Step 2） | → 询问：查看 / 编辑 / 重建 |
| 否 | → 说明尚未建立，引导进入新建模式（Step 4） | → 说明尚未建立，引导进入新建模式（Step 4） | → 进入新建模式（Step 4） |

### Step 2: 查看模式

展示当前人设概览：
```
🧑 创作人设档案 (.yang-persona.md v{version})
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📌 身份：{identity}
💡 核心价值观：{core_values}
📖 个人故事：{N} 个故事
🗣️ 口癖：{catchphrase}
😄 情绪表达：{emotion_examples}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
选填：自嘲 {self_deprecation} | 知识舒适区 {knowledge_zones} | 文化参照 {cultural_refs} | 幽默 {humor_style} | 称呼 {reader_name} | 结尾 {ending_pref} | 文风对标 {style_ref}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
输入「编辑人设」修改 | 输入任意内容继续当前会话
```

### Step 3: 编辑模式

> 🔍 **CHECKPOINT 1**：编辑目标字段已确认，变更原因已记录

展示当前人设概览（同上），然后询问：
"你想修改哪部分？说出字段名即可。例如：'修改身份'、'加个故事'、'改口癖'。

也可以说「全量重建」来完整重填。"

根据用户选择，引导修改对应字段，流程与新建时一致（引导型提问 + 故事清晰度检查 + 追问机制）。

修改后更新 `.yang-persona.md` 的 `updated_at` 和 `version`（版本号递增）。

**版本命名**：引导用户给本次修改的版本起名：
"给这个版本起个名字吧，方便以后回顾人设变化。比如「更口语化」「加入创业故事」「去爹味版」——跳过就用 v{N} 默认名。"

- 用户输入名称 → 写入 `persona_history` 的 `version_label` 字段
- 用户跳过 → `version_label` 默认设为 `v{N}`（N 为当前版本序号）

修改完成后，记录人设变更到 `.yang-state.json` 的 `persona_history` 数组：

```json
{
  "from_version": "v{旧版本号}",
  "to_version": "v{新版本号}",
  "version_label": "{用户输入的名称 或 v{N}}",
  "changed_at": "{ISO 8601 timestamp}",
  "reason": "{用户提供的变更原因简述}"
}
```

- `reason` 向用户询问："这次人设改动主要是因为什么？一句话就行，方便以后追溯"
- 若用户选择跳过 → `reason` 为 `"用户未提供原因"`
- 每次编辑都追加一条记录（即使只改一个小字段）

### Step 4: 新建模式

> 🔍 **CHECKPOINT 2**：必填项引导开始，逐项收集人设信息

引导用户进入人设填写流程。此流程与 yang-init Step 6.5 完全一致：

**引导语**：
"接下来帮你建立创作人设档案。
这会让你之后的文章更有「活人感」——读者会觉得是一个真人在说话，
而不是 AI 在输出信息。你也可以跳过，随时回来补充。

准备好了吗？先说第一项：你是谁？用一句话说清楚。"

**必填项（逐项引导）：**

1. **身份**："你是谁？用一句话说清楚。比如：做了三年AI内容的创业者 / 在大厂做过五年产品的独立开发者"
2. **核心价值观**："你相信什么？一句话。比如：技术应该让人更有创造力，而不是更焦虑 / 好的产品不需要说明书"
3. **个人故事（至少3个）**："现在说说你的故事。不是你简历上的经历，是那种有场景、有情绪、有转折的真实故事。先说第一个？"

   每个故事检查清晰度：是否包含时间地点？是否有情绪变化？是否有具体场景和细节？
   不满足 → 触发知识库追问（场景+感官/价值+共鸣/转折+行动）
   追问最多 2 轮，仍不清晰 → 标注 [待补充] 继续

4. **口癖/习惯用语**："你平时说话一定会用的词有哪些？不是书面语，是真·口语。比如有些人永远说'讲真'，有些人开口就是'巨'。你的是哪些？"
5. **情绪表达方式**：
   - 震惊的时候：_______（比如：我靠 / 天哪 / 真的假的）
   - 无语的时候：_______（比如：算了 / 行吧 / 就离谱）
   - 兴奋的时候：_______（比如：太爽了 / 牛啊 / 起飞）
   - 难过的时候：_______（比如：唉 / 破防了 / 整个人都不好了）

**选填项（可选逐项询问）：**
"必填项搞定了。还有 7 个选填项，填了效果会更好。每项都可以跳过，要逐项看看吗？(y/n)"

若用户选"y" → 逐项引导：自嘲方式、知识舒适区、文化参照系、幽默风格、读者称呼、结尾偏好、文风对标
若用户选"n" → 选填项留空，生成档案

**写入人设档案：**

> 🔍 **CHECKPOINT 3**：必填项收集完毕，选填项处理完成，准备写入档案

生成 `.yang-persona.md`：包含 YAML frontmatter（created_at/updated_at/version:"1.0"），按"必填/选填"分区，故事以 `### 故事 N` 标题逐段写入。

更新 `.yang-state.json`：`persona_exists: true`，`persona_version: "1.0"`，`persona_name: "{用户身份/名称}"`，`persona_history: []`（首次创建初始化为空数组，后续编辑时追加变更记录）。

**输出确认：**
```
🧑 创作人设已建立
📝 必填 5/5 · 选填 X/7
📁 .yang-persona.md v1.0
💡 随时说"编辑人设"来修改
```

## 人设变更记录

每次人设变更时，在 `.yang-state.json` 的 `persona_history` 数组中追加记录：

```json
{
  "from_version": "v1.0",
  "to_version": "v2.0",
  "changed_at": "{ISO 8601 timestamp}",
  "reason": "{变更原因}"
}
```

- `persona_history` 在首次建人设时初始化为 `[]`
- 每次编辑人设（Step 3）时追加一条记录
- `reason` 由用户提供（一句话简述），若用户跳过则记录 `"用户未提供原因"`
- `from_version` 和 `to_version` 从 `.yang-persona.md` frontmatter 的当前版本号读取

## 错误处理

| 场景 | 行为 |
|------|------|
| `.yang-state.json` 不存在 | 拒绝执行："请先运行 yang-init 初始化项目" |
| 用户输入无法匹配任何字段名 | 列出可选字段名："可选字段：身份、核心价值观、故事、口癖、情绪表达、自嘲方式、知识舒适区、文化参照系、幽默风格、读者称呼、结尾偏好、文风对标" |
| 版本号递增异常 | 从 `.yang-persona.md` frontmatter 中读取当前版本号，手动 +0.1 |

## 失败模式编码

| 编码 | 名称 | 描述 |
|------|------|------|
| `YP-E01` | 项目未初始化 | .yang-state.json 不存在，无法读取/写入人设状态 |
| `YP-E02` | 故事清晰度不足 | 个人故事缺少场景/情绪/转折，追问 2 轮后仍不清晰 |
| `YP-E03` | 必填项缺失 | 身份/核心价值观/故事/口癖/情绪表达任一未填写 |
| `YP-E04` | 版本冲突 | 编辑时 .yang-persona.md 版本号与 .yang-state.json 不一致 |
| `YP-E05` | 字段无法识别 | 用户输入无法匹配 12 个字段中的任何一个 |
| `YP-E06` | 人设空洞 | 必填项虽全但内容过于泛化（如"我是一个人"），无差异化信号 |

## 反例黑名单

1. **禁止在项目未 init 时建人设**——.yang-state.json 不存在则拒绝，引导先跑 yang-init
2. **禁止跳过必填项直接生成档案**——5 项必填缺一不可，缺则追问而非留空
3. **禁止将 AI 生成内容伪装为用户真实人设**——口癖/故事/情绪表达必须来自用户原话
4. **禁止静默覆盖人设档案**——编辑时必须展示变更 diff 并获得用户确认
5. **禁止删除 persona_history 历史记录**——变更记录是追溯人设演化的唯一依据
6. **禁止将选填项标为必填**——7 项选填不可强制要求，用户跳过是合法操作
7. **禁止在故事清晰度不足时标注为完成**——追问 2 轮后仍不清晰须标 [待补充]，不得假装清晰
8. **禁止跨版本直接覆盖**——每次编辑必须递增版本号并记录变更原因

## 特有量化标准：人设饱和度评分

人设档案完成后须计算**人设饱和度**，衡量档案对 yang-polish 活人感润色的支撑能力：

| 字段类别 | 权重 | 满分条件 |
|----------|------|----------|
| 必填完整度 | 50% | 5/5 必填项全部填写且非泛化内容 |
| 故事深度 | 20% | ≥3 个故事且无 [待补充] 标记 |
| 选填丰富度 | 15% | ≥4/7 选填项已填写 |
| 情绪覆盖度 | 15% | 4 种情绪表达（震惊/无语/兴奋/难过）全部有具体表达 |

| 饱和度等级 | 分值区间 | 含义 |
|------------|----------|------|
| 丰满 | ≥80% | yang-polish 可充分参考，活人感强 |
| 基础 | 50-79% | 可用但润色空间有限，建议补充选填项 |
| 骨架 | <50% | 仅满足最低要求，yang-polish 效果受限 |

饱和度评分写入 `.yang-persona.md` frontmatter 的 `saturation_score` 字段。yang-polish 调用人设时读取该分值，低于 50% 时主动提示"人设饱和度不足，润色效果可能有限"。

## 人设档案与polish的联动

> 人设档案是 yang-polish 活人感润色的核心输入。本段定义人设档案如何具体影响润色决策的规则，确保润色结果真正体现创作者的人格特征。

### 联动机制总览

```
.yang-persona.md
  ↓ 读取
yang-polish 润色引擎
  ↓ 应用规则
润色后内容（含人设特征标记）
```

### 人设字段对润色决策的影响规则

| 人设字段 | 影响的润色决策 | 具体规则 |
|---------|-------------|---------|
| 身份 | 开篇定位、权威感表达 | 润色时保留身份相关的权威引用，不替换为通用表述 |
| 核心价值观 | 论点倾向、价值判断 | 润色时不改变与核心价值观一致的论点方向 |
| 个人故事 | 举例方式、叙事风格 | 优先使用档案中的故事素材替代通用案例 |
| 口癖/习惯用语 | 口语化替换 | 将书面语替换为档案中的口癖（如"讲真"→保留，不改为"说实话"） |
| 情绪表达方式 | 情绪词选择 | 震惊/无语/兴奋/难过 → 使用档案中的具体表达，不替换为通用情绪词 |
| 自嘲方式 | 幽默感植入 | 在适当位置插入档案中的自嘲模式，不添加档案外的幽默 |
| 知识舒适区 | 专业术语使用 | 在舒适区内使用专业术语，区外用通俗解释 |
| 文化参照系 | 类比/引用选择 | 优先使用档案中的文化参照（如游戏/动漫/体育），不引入档案外的参照 |
| 幽默风格 | 笑点类型 | 按档案风格植入幽默（冷幽默/自嘲/反讽），不混入其他风格 |
| 读者称呼 | 称谓一致性 | 全文使用档案中的读者称呼（如"你"/"兄弟"/"朋友"），不混用 |
| 结尾偏好 | 收尾方式 | 按档案偏好选择结尾风格（金句/提问/行动号召/留白） |
| 文风对标 | 整体调性 | 润色整体调性向对标风格靠拢，不偏离 |

### 联动强度分级

| 饱和度 | 联动强度 | 润色行为 |
|--------|---------|---------|
| ≥80%（丰满） | 强联动 | 全面应用所有字段规则，润色后人设特征显著 |
| 50-79%（基础） | 中联动 | 应用必填项规则，选填项缺失的决策使用通用替代 |
| <50%（骨架） | 弱联动 | 仅应用身份+口癖+情绪表达，其余使用通用润色 |

### 联动冲突处理

当人设档案与内容类型冲突时：
- **身份与内容不匹配**（如"程序员"写"育儿"内容）→ 保留身份视角，用"跨界"叙事桥接
- **口癖与正式内容冲突**（如"讲真"出现在学术论述中）→ 保留口癖但调整语境，使其自然
- **情绪表达与内容基调冲突**（如"我靠"出现在严肃话题中）→ 降级为更温和的同义表达，保留情绪方向


## 人设饱和度评估

> 评估人设档案是否足够支撑内容生产的量化标准。本段扩展饱和度评估的维度和动态监控机制。

### 饱和度评分维度（扩展版）

| 维度 | 权重 | 满分条件 | 评分细则 |
|------|------|---------|---------|
| 必填完整度 | 35% | 5/5 必填项全部填写且非泛化 | 每缺 1 项 -7%；泛化内容（如"我是一个人"）按 50% 计 |
| 故事深度 | 20% | ≥3 个故事且无 [待补充] | 每个清晰故事 +6.7%；有 [待补充] 的故事按 50% 计 |
| 选填丰富度 | 15% | ≥4/7 选填项已填写 | 每填 1 项 +2.1%；填写但内容泛化按 50% 计 |
| 情绪覆盖度 | 15% | 4 种情绪表达全部有具体表达 | 每覆盖 1 种 +3.75%；"还行"/"一般"等泛化表达按 50% 计 |
| 口癖独特性 | 10% | 口癖非通用表达 | 通用口癖（"然后"/"就是"）按 30% 计；独特口癖（"巨"/"离谱"）按 100% 计 |
| 故事差异化 | 5% | 故事间无重叠主题 | 故事主题重叠 > 50% → 扣 2.5% |

### 饱和度等级与行动建议

| 等级 | 分值区间 | 内容生产支撑能力 | 行动建议 |
|------|----------|----------------|---------|
| 丰满 | ≥80% | yang-polish 可充分参考，活人感强 | 维护即可，定期检查是否过时 |
| 基础 | 60-79% | 可用但润色空间有限 | 优先补充选填项（自嘲/文化参照/幽默风格） |
| 骨架 | 40-59% | 仅满足最低要求，yang-polish 效果受限 | 必须补充故事细节和情绪表达 |
| 空壳 | <40% | 几乎无法支撑活人感润色 | 建议全量重建人设档案 |

### 饱和度动态监控

- 每次编辑人设后重新计算饱和度评分
- 饱和度变化写入 `persona_history` 的 `saturation_delta` 字段
- yang-status 看板展示当前饱和度等级
- 饱和度连续 2 次下降 → 提示"人设档案在缩水，建议检查是否删除了有效内容"
- 饱和度从 ≥80% 降至 <60% → 触发 yang-doctor 健康检查

### 饱和度与内容类型匹配度

不同内容类型对人设饱和度的最低要求不同：

| 内容类型 | 最低饱和度要求 | 关键依赖字段 |
|---------|--------------|-------------|
| 口播观点类 | 60% | 身份 + 口癖 + 情绪表达 + 核心价值观 |
| 故事叙事类 | 70% | 个人故事 + 情绪表达 + 结尾偏好 |
| 知识科普类 | 50% | 身份 + 知识舒适区 + 文风对标 |
| 情感共鸣类 | 80% | 全部字段（尤其是情绪表达 + 自嘲 + 故事） |

## 人设迭代规则

> 人设档案不是一成不变的，需要随创作实践不断迭代。本段定义什么情况下应该更新人设档案，以及迭代的规范流程。

### 触发人设迭代的条件

| # | 触发条件 | 检测方式 | 迭代类型 |
|---|---------|---------|---------|
| 1 | 创作者主动要求 | 用户说"编辑人设"/"修改人设" | 主动迭代 |
| 2 | yang-polish 反馈人设不匹配 | 润色后人设应用报告显示多处冲突 | 被动迭代 |
| 3 | 内容方向变化 | 连续 3 篇内容与档案中的知识舒适区/身份不匹配 | 建议迭代 |
| 4 | 口癖自然演变 | 最近 5 篇内容中出现了档案外的高频口癖 | 建议迭代 |
| 5 | 饱和度持续下降 | 饱和度评分连续 2 次下降 | 建议迭代 |
| 6 | 人设档案超过 90 天未更新 | 检查 `updated_at` 距今天数 | 建议审查 |
| 7 | yang-retro 复盘发现人设与受众不匹配 | 复盘数据显示"人设感弱"的反馈 | 建议迭代 |
| 8 | 重大生活事件 | 用户主动告知（如创业/转行/搬家） | 主动迭代 |

### 迭代规范流程

```
Step 1: 迭代触发
  → 识别触发条件（#1-#8）
  → 输出："检测到人设迭代信号：{原因}，建议更新人设档案"

Step 2: 变更评估
  → 展示当前人设概览
  → 询问："哪些部分需要调整？"
  → 识别变更范围：单字段 / 多字段 / 全量重建

Step 3: 变更执行
  → 单字段：引导修改目标字段
  → 多字段：逐项引导修改
  → 全量重建：走 Step 4 新建流程

Step 4: 版本管理
  → 递增版本号（+0.1）
  → 记录变更到 persona_history
  → 询问版本标签和变更原因

Step 5: 饱和度重算
  → 重新计算饱和度评分
  → 对比迭代前后饱和度变化
  → 输出："饱和度：{旧}% → {新}%（{↑/↓}）"

Step 6: 下游通知
  → 若饱和度等级变化 → 通知 yang-polish 调整联动强度
  → 若身份/核心价值观变更 → 通知 yang-recommend 调整推荐策略
  → 若口癖/情绪表达变更 → 通知 yang-polish 更新润色词库
```

### 迭代频率建议

| 频率 | 适用场景 | 迭代范围 |
|------|---------|---------|
| 每月 | 活跃创作者 | 审查口癖/情绪表达是否过时 |
| 每季度 | 稳定创作者 | 审查故事/知识舒适区是否需要补充 |
| 重大事件后 | 创业/转行/生活变化 | 全量审查，可能需要重建 |
| 内容方向转变时 | 新开内容线/换赛道 | 身份+知识舒适区+文风对标 |

### 迭代禁忌

1. **禁止删除历史版本**——persona_history 是追溯人设演化的唯一依据
2. **禁止在未确认时覆盖人设**——编辑时必须展示变更 diff 并获得用户确认
3. **禁止将 AI 生成内容伪装为用户真实人设**——所有迭代内容必须来自用户原话
4. **禁止跳过饱和度重算**——每次迭代后必须重新计算并记录饱和度变化
5. **禁止在迭代后不通知下游 skill**——人设变更可能影响 polish/recommend/status 的行为
