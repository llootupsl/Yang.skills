> **依赖**：无

## 失败模式编码

| 编码 | 名称 | 描述 |
|------|------|------|
| MIG-E01 | STATE_MISSING | `.yang-state.json` 不存在，无法执行迁移 |
| MIG-E02 | STATE_CORRUPT | state 文件 JSON 解析失败 |
| MIG-E03 | DOWNGRADE_BLOCKED | 目标版本低于当前版本，不允许降级迁移 |
| MIG-E04 | MIGRATION_STEP_FAILED | 单步迁移执行失败，需回滚 |
| MIG-E05 | VALIDATION_FAILED | 迁移后验证不通过，schema 字段缺失或类型错误 |
| MIG-E06 | BACKUP_FAILED | 迁移前备份创建失败，中止迁移 |

## 反例黑名单

1. **禁止降级迁移**：目标版本不得低于当前版本，不得删除已有字段（只允许新增/重命名/重构）
2. **禁止跳过中间版本**：必须按版本链依次执行每步迁移，不得从 v1.0 直接跳到 v2.0
3. **禁止无备份迁移**：迁移前必须创建 .bak 备份，备份失败则中止整个迁移
4. **禁止部分写入**：迁移步骤必须原子完成，中途失败必须回滚到备份版本
5. **禁止忽略验证失败**：迁移后验证不通过时，不得继续使用新文件，必须回滚
6. **禁止修改非目标字段**：迁移只允许操作 schema 变更涉及的字段，不得"顺便"修改其他字段值
7. **禁止在并发会话中迁移**：in_progress_session 不为 null 时必须警告用户，不得静默执行
8. **禁止删除备份文件**：迁移成功后备份文件保留，由用户手动清理

## 工作流

### Step 1: 检查当前版本

> 🔍 **检查点 CP-1**：确认 state 文件存在且 JSON 合法，版本号格式正确（v{major}.{minor}）

读取 `.yang-state.json` 中 `version` 字段，与目标版本比较。

若已是最新版本：
```
? 状态文件已是最新版本 (vX.Y.Z)，无需迁移。
```

### Step 2: 识别迁移路径

按版本链依次执行每步迁移：

| 版本变化 | 迁移操作 |
|---------|---------|
| 1.0.0 → 1.1.0 | 添加 `rubric_bumps` 字段（默认 0） |
| 1.1.0 → 1.2.0 | 添加 `benchmark_count` 字段 |
| 1.2.0 → 2.0.0 | `stats` 结构重构，添加 `accuracy_trend` 数组 |
| 自定义 | 用户指定 from/to，按规则迁移 |

### Step 3: 执行迁移

> 🔍 **检查点 CP-2**：确认迁移路径已识别，备份文件已创建成功

对每个迁移步骤：
1. 读取当前 state
2. 应用该步骤的数据转换
3. 写入中间状态

### Step 4: 备份 & 写入

> 🔍 **检查点 CP-3**：确认备份文件存在且内容完整（可反序列化）

- 迁移前：自动备份为 `.yang-state.json.bak.<old-version>`
- 迁移后：写入新文件，version 更新为目标版本

### Step 5: 验证

> 🔍 **检查点 CP-4**：验证新文件 JSON 合法，所有必需字段存在且类型正确
> 🔍 **检查点 CP-5**：对比迁移前后字段数量，确认新增字段已写入、已有字段未丢失

## 量化标准：迁移完整性校验清单

迁移完成后，必须逐项校验以下完整性指标，全部通过方可标记为"迁移成功"：

| # | 校验项 | 通过条件 |
|---|--------|---------|
| 1 | JSON 合法性 | 新文件可被 `JSON.parse()` 无报错解析 |
| 2 | 版本号更新 | `schema_version` 已更新为目标版本 |
| 3 | 新增字段存在 | 迁移步骤中定义的新增字段全部存在于新文件中 |
| 4 | 已有字段保留 | 迁移前存在的字段在新文件中未丢失（值不变） |
| 5 | 默认值正确 | 新增字段的默认值符合 schema 定义 |
| 6 | 备份可恢复 | 备份文件可被反序列化，内容与迁移前一致 |
| 7 | 字段数量校验 | 新文件字段数 = 旧文件字段数 + 新增字段数 - 删除字段数 |

**校验输出格式**：
```
✅ 迁移完整性校验：7/7 通过
  JSON合法性 ✅ | 版本号 ✅ | 新增字段 ✅ | 已有字段 ✅ | 默认值 ✅ | 备份可恢复 ✅ | 字段数量 ✅
```

## 迁移前备份验证

> 迁移前必须验证备份的完整性和可恢复性，确保迁移失败时能安全回滚。本段定义备份验证的 5 项检查。

### 备份验证检查清单

| # | 检查项 | 通过条件 | 不通过处理 |
|---|--------|---------|-----------|
| 1 | 备份文件存在 | `.yang-state.json.bak.<version>` 文件已创建 | 中止迁移，重新创建备份 |
| 2 | 备份 JSON 合法 | 备份文件可被 `JSON.parse()` 无报错解析 | 中止迁移，检查原始文件是否已损坏 |
| 3 | 备份内容完整 | 备份文件的字段数与迁移前 state 文件一致 | 中止迁移，重新创建备份 |
| 4 | 备份可反序列化 | 备份文件的所有字段值与迁移前 state 完全一致（逐字段比对） | 中止迁移，删除损坏备份并重新创建 |
| 5 | 备份写入路径可访问 | 备份文件所在目录可写，且无同名文件覆盖风险 | 中止迁移，清理路径后重试 |

### 备份验证流程

```
Step 1: 创建备份
  → 写入 .yang-state.json.bak.<old-version>

Step 2: 验证备份
  → 检查项 1-5 逐项执行
  → 全部通过 → 进入迁移流程
  → 任一不通过 → 中止迁移，输出：
    "❌ 备份验证失败（{N}/5 通过）：
      · {失败项}: {具体原因}
      迁移已中止，请修复后重试。"

Step 3: 备份验证通过后
  → 输出："✅ 备份验证通过（5/5），备份路径：{path}"
  → 进入迁移执行流程
```

### 备份保留策略

- 迁移成功后备份文件**不删除**，由用户手动清理
- 多次迁移产生多个备份文件，按版本号命名（如 `.yang-state.json.bak.1.0.0`、`.yang-state.json.bak.1.1.0`）
- 若备份文件已存在（同版本），追加时间戳而非覆盖：`.yang-state.json.bak.1.0.0.20260517`

## 迁移后功能验证

> 迁移完成后必须验证系统功能正常，确保所有依赖 state 文件的 skill 可正常工作。本段定义迁移后的功能验证清单。

### 功能验证清单

| # | 验证项 | 验证方式 | 预期结果 | 失败处理 |
|---|--------|---------|---------|---------|
| 1 | state 文件可读 | `JSON.parse()` 解析新文件 | 无报错 | 回滚到备份 |
| 2 | schema_version 已更新 | 读取 `schema_version` 字段 | 等于目标版本 | 回滚到备份 |
| 3 | 新增字段存在且默认值正确 | 逐字段检查新增字段 | 全部存在且值符合 schema | 运行 `yang-doctor --fix` 补齐 |
| 4 | 已有字段值未变更 | 逐字段比对迁移前后值 | 所有已有字段值不变 | 回滚到备份 |
| 5 | yang-status 可正常读取 | 运行 `yang-status` | 无报错，buffer/校准数据正确显示 | 检查字段语义约束 |
| 6 | yang-predict 可正常写入 | 模拟预测流程（dry-run） | 可正常创建预测文件 | 检查 state 字段引用 |
| 7 | yang-shoot 可正常登记 | 检查 shoots 数组结构 | 数组可正常追加条目 | 检查 shoots 字段结构 |
| 8 | yang-recommend 可正常排序 | 运行 `yang-recommend --top 1` | 可正常输出推荐 | 检查 rubric/candidates 引用 |
| 9 | yang-retro 可正常复盘 | 检查 calibration_records 结构 | 结构完整可读取 | 检查 calibration 字段 |
| 10 | yang-doctor 全量诊断 | 运行 `yang-doctor` | 无 🔴 严重项 | 按 yang-doctor 建议修复 |

### 功能验证执行顺序

```
Step 1: 基础验证（#1-#4）
  → 任一失败 → 立即回滚
  → 全部通过 → 继续

Step 2: skill 功能验证（#5-#9）
  → 任一失败 → 尝试 yang-doctor --fix 自动修复
  → 修复后仍失败 → 回滚

Step 3: 全量诊断（#10）
  → 有 🔴 严重项 → 尝试修复
  → 修复后仍有 🔴 → 回滚
  → 无 🔴 → 迁移成功确认

Step 4: 输出验证结果
  → "✅ 迁移后功能验证：10/10 通过"
  → 或 "⚠️ 迁移后功能验证：N/10 通过，需修复：{列表}"
```

## 回滚操作手册

> 迁移失败或迁移后功能异常时，必须按本手册执行回滚，恢复到迁移前的稳定状态。

### 回滚触发条件

| 条件 | 触发方式 |
|------|---------|
| 迁移步骤执行失败（MIG-E04） | 自动触发 |
| 迁移后验证不通过（MIG-E05） | 自动触发 |
| 迁移后功能验证失败 | 手动触发 |
| 用户主动要求回滚 | 手动触发 |

### 回滚步骤

```
Step 1: 确认备份文件存在
  → 读取 .yang-state.json.bak.<old-version>
  → 不存在 → ❌ 无法回滚（备份丢失），需手动重建 state
  → 存在 → 继续

Step 2: 验证备份完整性
  → JSON.parse() 解析备份文件
  → 解析失败 → ❌ 备份损坏，需手动修复
  → 解析成功 → 继续

Step 3: 创建当前（损坏）state 的快照
  → 将当前 .yang-state.json 复制为
    .yang-state.json.failed-migration.<timestamp>
  → 保留失败状态供事后分析

Step 4: 恢复备份
  → 将 .yang-state.json.bak.<old-version> 复制为 .yang-state.json
  → 原子操作：先写 .tmp → 验证 → rename

Step 5: 验证恢复
  → JSON.parse() 解析恢复后的文件
  → schema_version 应为旧版本
  → 所有字段与备份一致

Step 6: 清理 in_progress_session
  → 若回滚前有残留的 in_progress_session → 清除
  → 设置为 null

Step 7: 输出回滚结果
  → "✅ 回滚完成：{new_version} → {old_version}"
  → "备份来源：.yang-state.json.bak.{old-version}"
  → "失败快照：.yang-state.json.failed-migration.{timestamp}"
  → "建议：检查失败原因后重新执行迁移"
```

### 回滚后检查

回滚完成后须执行以下检查：

1. 运行 `yang-doctor` 确认系统健康度恢复
2. 检查 `predictions/*.md` 和 `videos/` 目录是否受影响（迁移不应修改这些文件，但需确认）
3. 检查 `candidates.md` 和 `rubric_notes.md` 是否受影响
4. 确认 buffer 计数与 shoots 队列一致

### 回滚失败应急方案

若回滚本身也失败（如备份损坏）：

1. 检查是否有更早版本的备份文件
2. 从 `predictions/*.md` 和 `videos/` 目录重建关键 state 字段
3. 运行 `yang-init` 重建 state 文件（最后手段，会丢失部分历史数据）
4. 手动补齐 `calibration_records`、`persona_history` 等不可重建的字段
