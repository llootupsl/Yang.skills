# yang-trends · 热点趋势抓取

## ⚡ 紧凑核心规则

**多源聚合**：优先fetch_trends.py零配置聚合（微博/知乎/B站/百度/抖音/头条/IT之家/36氪）→ 搜索意图适配器search_intent.py补充（搜索建议/相关搜索/问题型需求/长尾词/趋势查询/内容空白检测）→ TrendRadar MCP增强 → Agent WebFetch兜底 → 仅Channel A/B。单源失败自动跳过，全部失败才降级。

**时效标注**：以运行此刻为锚点，过去2h内🔴紧急 | 2-12h🟠热 | 12-24h🟢新 | >24h⚪消退中。绝不用过期热榜冒充当天，每次运行刷新锚点。

**相关性阈值**：关键词精确匹配40%+模糊20%+语义30%+时效10%→总分≥0.6🎯高相关 | 0.3-0.59📌中相关 | <0.3❌过滤。端到端转化率9-21%，<5%提示扩大关键词。

> **前置条件**：项目已 init，trend-sources adapter 已配置
>
> **产生**：candidates.md 更新（新增热点选题）
>
> **依赖**：adapters/trend-*/（热点数据源适配器）

## 降级链

按以下优先级降级：
1. **多源聚合器 `adapters/trend-sources/fetch_trends.py`** → 最优先，零配置直接运行：一条命令并行抓取 微博/知乎/B站/百度/抖音/头条/IT之家/36氪 等公开热榜，自带时效锁与优雅降级，**无需 cookie/token/MCP/任何用户配置**。
2. **搜索意图适配器 `adapters/search-intent/search_intent.py`** → 补充搜索意图信号，发现"有人搜但没人做好"的选题机会（零API Key，公开端点）。
3. **TrendRadar MCP**（可选增强）→ 若用户已注册该 MCP，可作结构化热度曲线补充。
4. **Agent 自身 WebFetch 兜底** → 仅当聚合器全部源都不可用（网络受限/端点临时变更）时，由 Claude 用 WebFetch 直接抓取平台热搜页解析。
5. **仅 Channel A/B** → 以上全部不可用时，仅输出 Channel A/B 选题，并提示「暂时无法获取热点，建议手动浏览平台热搜」。

> 设计原则：开放搜索源应"开箱即用"。聚合器只调公开匿名端点 + 浏览器 UA，单源失败不影响其余源；调用方无需预先配置任何数据源目录。

**本地降级调用**：当fetch_trends.py全部源失败时，自动调用local_trends.py从本地.md/.json文件读取热点数据。调用方式：`python adapters/trend-sources/local_trends.py --out candidates/trends_local.json`。本地数据输出格式与fetch_trends.py完全一致，上层无需修改。输出标注"⚠ 数据非实时"。

## 工作流

### Step 1: 确定热点源

根据用户配置和参数确定热点数据源：

| 平台 | 典型数据源 |
|------|-----------|
| 抖音 | 抖音热榜、Douyin API |
| 小红书 | 小红书热搜 |
| B站 | B站热门榜 |
| 微博 | 微博热搜榜 |
| 知乎 | 知乎热榜 |
| 微信 | 微信指数 / 视频号热门 |
| 搜索引擎 | 百度搜索建议/相关搜索、Google搜索建议、必应搜索建议 |
| 知识问答 | 知乎问题搜索、百度知道 |

> **✅ 检查点 1**：确认至少有一个可用热点源。若用户指定了 `--platform` 但该平台源不可用，立即警告并建议替代源，不要静默跳过。

### Step 2: 拉取热点（零配置多源聚合器）

直接运行聚合器，一条命令拉全部公开热榜并落盘：

```bash
# 全部默认源（微博/知乎/B站/百度/抖音/头条），每源 30 条
python adapters/trend-sources/fetch_trends.py --limit 30 --out candidates/trends_raw.json

# 指定源 + 垂直关键词预筛（例：只要标题含"考研"的热点）
python adapters/trend-sources/fetch_trends.py --sources weibo,zhihu,bilibili --keyword 考研 --out candidates/trends_raw.json
```

可选源：`weibo, zhihu, bilibili, baidu, douyin, toutiao, ithome, 36kr`。输出每条含 `title / source / url / hotness / rank / _freshness / snapshot_at`，并在 `meta` 里记录运行锚点、成功源、失败源。

- **单源失败自动跳过**，其余源照常返回；只有所有源都失败才非零退出 → 此时回退到 Agent WebFetch（见降级链第 4 档）。
- **增强（可选）**：若用户注册了 [TrendRadar](https://github.com/sansan0/TrendRadar) MCP，可叠加其结构化热度曲线。

> **✅ 检查点 2**：验证 `trends_raw.json` 已生成且非空。若文件为空或不存在，触发降级链第 4 档（Agent WebFetch 兜底），并记录失败源到 `.yang-state.json` 的 `error_log`。

### Step 2.5: 拉取搜索意图信号（零配置搜索意图适配器）

在热榜数据基础上，补充搜索意图信号——发现"有人搜但没人做好"的选题机会：

```bash
# 从rubric提取种子词后，拉取搜索意图信号
python adapters/search-intent/search_intent.py --keyword "种子词" --limit 20 --out candidates/search_intent.json
```

搜索意图信号与热榜信号的区别：
- 热榜 = 已热（高竞争、短窗口、适合追打）
- 搜索意图 = 将热/未热（低竞争、长窗口、适合中小账号切入）

两种信号互补，不应只用一种。

### Step 3: 相关性筛选

筛出与用户垂直领域相关的热点：

1. 关键词匹配：用户 rubric 中的主题标签 vs 热点关键词
2. 语义相关性：大模型判断热点与用户领域的关联度（高/中/低/无关）
3. 过滤无关热点

**热点相关性评分标准**：

| 维度 | 权重 | 评分规则 |
|------|------|----------|
| 关键词精确匹配 | 40% | 热点标题/标签与用户 rubric 主题标签精确匹配，每匹配 1 个关键词 +0.4，上限 1.0 |
| 关键词模糊匹配 | 20% | 热点标题包含用户领域同义词/近义词（基于 jieba 分词 + 同义词表），每匹配 +0.2，上限 0.6 |
| 语义相关性 | 30% | 大模型判定：高相关（0.3）/ 中相关（0.15）/ 低相关（0.05）/ 无关（0） |
| 时效性加成 | 10% | 🔴 紧急 +0.1 / 🟠 热 +0.07 / 🟢 新 +0.03 / ⚪ 消退中 +0 |

**相关性等级判定**：
- 总分 ≥ 0.6 → 🎯 高相关（推荐追热点）
- 总分 0.3–0.59 → 📌 中相关（可选切入，需独特角度）
- 总分 < 0.3 → ❌ 低相关（不推荐，过滤掉）

**搜索意图信号的权重调整**：
- 问题型需求权重 +20%（更精准，反映真实用户需求）
- 长尾词权重 +10%（更低竞争，适合中小账号切入）

> **✅ 检查点 3**：确认至少有 1 条热点相关性评分 ≥ 0.3。若全部 < 0.3，触发 `TRENDS_NO_RELEVANT` 失败模式。

### Step 4: 时效性标记（时效锁）

热榜本身就是"当下"，但仍以**运行此刻为锚**统一标注，并把聚合器写入的 `_freshness` / `snapshot_at` 透传到产出（依据 `shared-protocols/freshness-protocol.md`）。展示用的时效窗口：

| 窗口（距抓取锚点） | 标记 |
|------|------|
| 过去 2 小时内 | 🔴 紧急 |
| 过去 12 小时内 | 🟠 热 |
| 过去 24 小时内 | 🟢 新 |
| 超过 24 小时 | ⚪ 消退中（不推荐追） |

> 对带单条发布时间的源（如 B站热门、IT之家 RSS）用真实 `publish_date` 判定；无单条时间的纯热榜（微博/百度/抖音词条）标 `unknown`，以 `snapshot_at` 为准，并提示"热点窗口短、请尽快产出"。绝不把昨天抓的榜当成今天的榜——每次运行都会刷新锚点。

### Step 5: 生成热点切入角度

对每个筛出的相关热点，生成 1-2 个独特的切入角度：

```
🔥 热点: <标题>
📈 热度: <指标>
🎯 相关性: 高（评分: 0.XX）
💡 你的切入角度:
  1. <角度A> — 结合你的领域知识和人设
  2. <角度B> — 从不同立场/视角解读
```

> **✅ 检查点 4**：确认每个切入角度都明确关联了用户的垂直领域或人设特征。若角度过于泛化（任何领域都适用），需重新生成。

### Step 6: 写入 candidates.md

将热点选题追加到 `candidates.md` 的 `## 热点选题` 区，标记为 Channel C（Hot-Surf）。

> **✅ 检查点 5**：验证 `candidates.md` 已成功更新，新增热点条目数与筛选结果一致。

## 失败模式编码

| 编码 | 含义 | 触发条件 | 恢复策略 |
|------|------|----------|----------|
| `TRENDS_ADAPTER_MISSING` | 热点适配器缺失 | `adapters/trend-sources/` 不存在或 `fetch_trends.py` 不可执行 | 提示用户安装适配器或手动输入热点；降级到 WebFetch 兜底 |
| `TRENDS_ALL_SOURCES_FAILED` | 所有热点源均失败 | 聚合器返回非零退出码，且 WebFetch 兜底也无法获取数据 | 输出本地缓存候选热点（标注"数据非实时"）；提示用户稍后重试 |
| `TRENDS_NO_RELEVANT` | 无相关热点 | 所有抓取热点相关性评分 < 0.3 | 提示"当前无与你领域相关的热点"；不更新 candidates.md；建议扩大关键词范围或稍后重试 |
| `TRENDS_STALE_CACHE` | 缓存数据过期 | 本地缓存热点距上次抓取超过 24 小时 | 强制重新抓取；若抓取失败，输出缓存数据并标注"⚠️ 数据非实时，最后更新: <时间>" |
| `TRENDS_RATE_LIMITED` | 热点源限流 | 聚合器返回 429 或连接超时 | 自动切换到降级链下一档；记录限流源到 `error_log`；建议用户间隔 10 分钟后重试 |

## 反例黑名单

> 以下行为严格禁止，任何一条违反都应视为 bug：

1. **不要用过期热榜当今天的**：绝不使用 `snapshot_at` 超过 24 小时的缓存数据冒充实时热点，每次运行必须刷新锚点
2. **不要推荐与领域无关的热点**：相关性评分 < 0.3 的热点不得写入 `candidates.md`，即使用户领域很宽泛也要走评分流程
3. **不要跳过时效锁**：每条热点必须标注时效窗口（🔴🟠🟢⚪），不得省略或用模糊描述替代
4. **不要伪造热度数据**：`hotness` / `rank` 必须来自数据源原始值，不得凭感觉编造或调整排名
5. **不要忽略单源失败**：即使只有 1 个源失败，也必须在输出报告中标注该源失败，不得静默跳过
6. **不要在无 rubric 时猜测领域**：若 `rubric_notes.md` 不存在或为空，必须先提示用户完善 rubric，不得自行推断垂直领域
7. **不要重复写入相同热点**：写入 `candidates.md` 前必须去重（按标题 + 源匹配），避免同一热点多次追加
8. **不要跳过相关性评分直接推荐**：即使热点看起来"很明显相关"，也必须走完评分流程并记录评分，确保可追溯

## 热点追打节奏

> 不同时效等级的热点有不同的内容产出时间窗口，必须按节奏执行，错过窗口则放弃该热点。

**时效等级与追打节奏**：

| 时效等级 | 可用窗口 | 内容产出时限 | 推荐内容类型 | 策略 |
|---------|---------|------------|------------|------|
| 🔴 紧急 | 0-6h | **2h 内产出** | 短评/观点切片/转发带评论 | 极速响应，用现有素材+热点观点快速拼接，牺牲精致度换时效 |
| 🟠 热 | 6-24h | **8h 内产出** | 观点型视频/图文/直播切片 | 有时间做基础脚本，但不宜深度打磨；优先保证角度独特性 |
| 🟢 新 | 1-3d | **24h 内产出** | 知识型/过程型内容 | 有充分时间做脚本和拍摄；可做深度解读或对比分析 |
| ⚪ 消退中 | 3d+ | **不追** | — | 热点已过窗口期，追打收益极低；转为常规选题储备 |

**追打节奏执行规则**：

1. **窗口倒计时机制**：每条热点标注 `deadline: <ISO timestamp>`（= 抓取时间 + 可用窗口），超时自动标记为 `⏰ 已过期`
2. **并行追打上限**：同一时间最多追打 2 个热点（避免质量稀释），按相关性评分排序取 Top 2
3. **追打成本评估**：
   ```
   📊 追打成本评估
     热点: <标题>
     时效等级: <🔴/🟠/🟢>
     可用窗口: <X>h
     预计产出时间: <Y>h
     是否可追: ✅ 可追（Y < 窗口）/ ❌ 不可追（Y > 窗口）
     推荐内容类型: <类型>
   ```
4. **放弃规则**：若评估后发现无法在窗口内产出 → 标记为 `🚫 窗口不足，放弃`，不强行追打
5. **追打后验证**：追打内容发布后 24h 内检查数据，若互动率低于近 5 条均值 50% → 标记为"热点追打失败"，记录原因

**追打节奏与发布排期的协调**：
- 若当前有排期内容 → 评估是否插队（紧急热点可插队，热/新热点排队）
- 插队规则：紧急热点可推迟 1 条排期内容，但不超过 1 条（避免打乱节奏）
- 插队后需更新发布排期表

## 热点-选题转化率

> 从热点到有效选题的转化规则和预期转化率，避免"追了很多热点但选题质量低"的问题。

**转化流程**：

```
原始热点 → 相关性筛选 → 角度生成 → 选题评估 → 有效选题
   100%       ↓ 30-50%      ↓ 60-70%     ↓ 50-60%   ↓ 9-21%
           (相关性过滤)   (角度可行性)  (选题质量)
```

**预期转化率**（基于历史数据参考）：

| 阶段 | 输入 | 输出 | 转化率 | 淘汰原因 |
|------|------|------|--------|---------|
| 原始热点 → 相关热点 | 全部热点 | 相关性 ≥ 0.3 | 30-50% | 与垂直领域无关 |
| 相关热点 → 可行角度 | 相关热点 | 有独特切入角度 | 60-70% | 无法找到独特角度/角度过于泛化 |
| 可行角度 → 有效选题 | 可行角度 | 通过选题质量评估 | 50-60% | 选题与已有内容重复/执行难度过高 |
| **端到端** | **原始热点** | **有效选题** | **9-21%** | — |

**选题质量评估标准**（可行角度 → 有效选题的过滤条件）：

| 评估维度 | 权重 | 评分规则 | 门槛 |
|---------|------|---------|------|
| **领域契合度** | 30% | 选题与用户垂直领域的深度关联度 | ≥ 0.6 |
| **人设一致性** | 25% | 选题是否匹配用户创作人设（口吻/立场/风格） | ≥ 0.5 |
| **差异化程度** | 25% | 与同领域已有内容的区分度（避免同质化） | ≥ 0.5 |
| **执行可行性** | 20% | 用户是否有能力/资源在窗口内完成 | ≥ 0.4 |

- 总分 ≥ 0.6 → ✅ 有效选题，写入 candidates.md
- 总分 0.4-0.59 → ⚠️ 待定选题，写入 candidates.md 但标注 `[待定]`
- 总分 < 0.4 → ❌ 淘汰，不写入

**转化率监控**：
- 每 10 次热点抓取后，统计实际转化率
- 若端到端转化率 < 5% → 提示"热点转化率偏低，建议：① 扩大垂直领域关键词范围 ② 降低相关性门槛至 0.25 ③ 增加角度生成的创意投入"
- 若端到端转化率 > 25% → 提示"热点转化率较高，可考虑提高选题质量门槛以筛选更优质选题"

**选题去重规则**：
- 与 candidates.md 中已有选题的相似度 > 0.8 → 合并为同一选题，追加新角度
- 与近 30 天已发布内容的主题相似度 > 0.7 → 标注 `[近期已覆盖]`，降低优先级

## 跨平台热点交叉验证

> 一个热点在多个平台同时出现时，通过交叉验证判断其真实热度和可持续性，避免被单一平台的热度泡沫误导。

**交叉验证触发条件**：
- 同一热点在 ≥ 2 个平台的热榜中出现 → 自动触发交叉验证
- 用户手动指定需验证的热点 → 触发交叉验证

**验证维度**：

| 维度 | 权重 | 检查内容 | 判定规则 |
|------|------|---------|---------|
| **平台覆盖度** | 30% | 热点出现在多少个平台 | 1个平台=0.1, 2个=0.2, 3个=0.25, 4个+=0.3 |
| **热度一致性** | 25% | 各平台排名/热度指标的相对位置 | 排名差异 < 30% → 0.25; 30-60% → 0.15; > 60% → 0.05 |
| **时效同步性** | 20% | 热点在各平台出现的时间差 | 时间差 < 2h → 0.2; 2-6h → 0.12; 6-12h → 0.06; > 12h → 0.02 |
| **用户参与深度** | 15% | 各平台评论/讨论的深度（非仅浏览） | 多平台有深度讨论 → 0.15; 仅浏览无讨论 → 0.05 |
| **内容形态多样性** | 10% | 热点在不同平台的内容形态（图文/视频/讨论） | ≥ 3种形态 → 0.1; 2种 → 0.06; 1种 → 0.02 |

**交叉验证评分与判定**：

| 总分 | 热度判定 | 标记 | 追打建议 |
|------|---------|------|---------|
| ≥ 0.7 | 🔥 全网热点 | `CROSS_PLATFORM_CONFIRMED` | 高优先级追打，窗口可能较长（24-48h） |
| 0.4-0.69 | 📈 平台间热点 | `CROSS_PLATFORM_PARTIAL` | 中等优先级，选择用户主平台追打 |
| 0.2-0.39 | 📊 单平台热点 | `SINGLE_PLATFORM_ONLY` | 低优先级，仅在用户主平台出现时考虑 |
| < 0.2 | 💤 伪热点/局部热点 | `LIKELY_BUBBLE` | 不建议追打，可能为平台推荐算法人为放大 |

**交叉验证输出格式**：

```
🔍 跨平台热点交叉验证

热点: <标题>
验证平台: <平台列表>

验证结果:
  平台覆盖度: <得分> (<详情：各平台排名>)
  热度一致性: <得分> (<详情：排名差异>)
  时效同步性: <得分> (<详情：各平台出现时间>)
  用户参与深度: <得分> (<详情：评论/讨论情况>)
  内容形态多样性: <得分> (<详情：各平台内容形态>)

综合评分: <X> / 1.0
热度判定: <🔥全网热点 / 📈平台间热点 / 📊单平台热点 / 💤伪热点>
标记: <CROSS_PLATFORM_CONFIRMED / ...>

追打建议: <具体建议>
```

**伪热点识别信号**（出现以下任一即提高警惕）：
1. 仅在单一平台出现，且该平台为算法推荐驱动型（如抖音热榜）→ 可能是算法放大
2. 排名极高但评论数极少（浏览/评论比 > 1000:1）→ 用户参与度低，热度不可持续
3. 热点出现时间与平台推荐位更新时间高度吻合 → 可能是平台运营干预
4. 相关搜索词无自然增长（百度指数/微信指数未同步上升）→ 非真实用户需求驱动

**交叉验证与追打节奏的联动**：
- `CROSS_PLATFORM_CONFIRMED` → 可适当延长追打窗口（+50%），因全网热点衰减更慢
- `SINGLE_PLATFORM_ONLY` → 收紧追打窗口（-30%），单平台热度衰减更快
- `LIKELY_BUBBLE` → 不追打，但记录观察（若后续出现跨平台扩散可升级）
